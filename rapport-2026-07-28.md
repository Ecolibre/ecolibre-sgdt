## 3. Ce qui a échoué ou n'a pas pu être obtenu

### 3.1 Contrôle visuel de l'Action S (info-bulles du formulaire)

Le lot demandait d'ouvrir `Spécial:AjouterDonnées/Physical item/Test
affichage` et de vérifier visuellement l'affichage des deux textes. Aucune
extension navigateur disponible dans cette session (proposée puis déclinée
par l'utilisateur). Contournement tenté par `curl` :

- Fetch anonyme de la page : rendu HTML récupéré (21 990 octets), mais
  formulaire désactivé (`disabled=""` sur tous les champs) avec message de
  permission — l'édition anonyme nécessite une adresse courriel confirmée et
  le groupe `Utilisateurs`, plus un CAPTCHA.
- Fetch avec les cookies de session du bot (`.cookies.txt`, mêmes cookies
  qui fonctionnent pour les écritures `action=edit` via l'API) : résultat
  strictement équivalent, `wgUserName: null` dans les deux cas, même mur de
  permission. Le compte bot semble donc traité comme anonyme sur ce point
  d'entrée `index.php`/`Special:FormEdit` précis, alors qu'il est authentifié
  côté `api.php`.
- Dans les deux versions de la page récupérée, **aucune trace textuelle**
  des deux info-bulles attendues (`grep` sur des fragments comme « modifier
  uniquement », « Calculé automatiquement », recherche de tout attribut
  `title=`, `data-*` ou clé JS contenant « description ») : rien trouvé.

**Conclusion :** l'info-bulle Page Forms semble injectée côté client par les
modules ResourceLoader (`ext.pageforms.main` etc.) après exécution du
JavaScript, donc invisible à un `curl` qui ne récupère que le HTML servi. Le
changement wikitexte (§1.1) est vérifié correct dans sa source, mais le rendu
effectif reste **non confirmé** — à vérifier par Cyril dans un vrai
navigateur.
